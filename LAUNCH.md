## What OpenChoice is built for, and when to use something else (positioning for every channel)

Say this plainly when asked "why not X?"; it mirrors the README section "What OpenChoice is built for, and when to use something else". Present OpenChoice's cases as design goals with benchmark results to follow, not as proven wins:

- **Short-text routing on any laptop:** a much smaller encoder such as Laya (~0.6–0.8 GB weights, 4–5 GB RAM minimum per Unsloth; one click via Unsloth Desktop) or GLiNER2.5-Decide (340M parameters). Latency was not compared.
- **Smallest GGUF with an official score:** the 4B GGUFs (JevK5, Plumb) are smaller and already have official JevBench v1.5.1 composites (71.9 / 71.6). OpenChoice's is pending.
- **Highest accuracy:** Jev, or Cygnet / Winnow-12B (v1.5.1 composites 72.1 / 73.7 / 73.2).
- **OpenChoice** is designed for decisions over long inputs (4,096 tokens per forward, 32,768 per decision), over charts on a CPU (Python engine), or tuned to your own policy and exported back to the same GGUF runtime. Benchmark results for these are still to come.

## Announcement blog post

### OpenChoice-9B: a decision model that fits on the computer you already have

Many "should this happen?" calls in software are small decisions: is this message a refund request, which of four tools fits, how risky is this change on a 1–5 scale. Sending each one to a hosted model costs money and latency, and it sends your data somewhere else. OpenChoice-9B is our attempt at a local alternative: a model that does one thing, turning a question plus options into probabilities, and does it on an ordinary CPU.

**What it is.** OpenChoice-9B starts from Qwen/Qwen3.5-9B and adds a rank-16 LoRA decision adapter. For release we merged the adapter and quantized the result to a 5.24 GiB GGUF (Q4_K_M), served by a pinned llama.cpp build through a small C++ bridge. It never generates text. For a Choice question it reads the logits of the answer letters and softmaxes them; Yes/No uses the Yes−No logit difference; Score normalizes over up to ten levels. You get one probability per option.

**It runs on a CPU.** On our desktop Ryzen 9 7900X3D, using 12 of its 24 threads, the model peaks at 6.1 GiB of RAM and answers a 300–600-token decision in 1.7–3.3 seconds. The GPU is untouched: nvidia-smi shows no process and the service uses 0 MiB of VRAM. That is not interactive-chat speed, and long prompts cost more (a 3,700-token decision took 20.8 seconds), but it is fast enough for background checks, routing and queued judging, and it keeps working when the GPU is busy with something else.

**The GPU is optional.** If you do have spare VRAM, `--gpu auto` adds a small four-layer offload that uses about 1.9 GiB. A 600-token decision drops from 3.28 to 1.02 seconds. The CPU instance never unloads: when a game or another job needs the VRAM, the GPU instance is released and the CPU instance keeps serving, then the offload returns after about a minute of free memory. In our tests the GPU and CPU paths agreed on 49 of 50 decisions.

**Charts on CPU.** A 595 MiB Q8_0 vision projector sits next to the text model, so OpenChoice can read charts without a GPU. On our 60-question synthetic chart development set it scored 49/60 on CPU. Chart input currently goes through the Python engine; the HTTP API is text-only, and charts are the only images we have evaluated.

**A familiar API.** The server implements the TypeSafe SDK 0.6 wire format at `POST /v1/systemone`, so existing SDK code can point at `localhost`. Compatibility means the request and response format only; we are not affiliated with TypeSafe, and OpenChoice is not a Jev model.

**Make it yours.** The repository includes a fine-tuning kit: validate your labeled decisions, train a LoRA, compare it against the released model on held-out rows, and export. Export produces the same GGUF package the release uses, with a manifest of relative paths and sha256 hashes, so your model serves with the same command on the same CPU. In the included tutorial, a self-authored company policy, the exported model answered 61 of 64 differently worded held-out questions correctly, up from 28 for the released model. Training needs a CUDA GPU (35 minutes on a rented 24 GB card for that run); serving the result does not.

**How good is it?** We re-measured the released GGUF on CPU and report everything with provenance in RESULTS.md, separating what we measured from what authors published. On 1,000 held-out SciQ questions it scores 95.3%, against 58.7% for CLM-v0.1-8B, which we ran ourselves. Its official JevBench v1.5.1 score is pending: the sealed split needs a maintainer submission. It is not the smallest decision model (Plumb-4B ships a 2.7 GB GGUF), and other releases such as Winnow-12B also combine GGUF, vision and the same API. What OpenChoice offers is the combination in one package: CPU-first GGUF, chart input on CPU, a TypeSafe-compatible API, and a fine-tuning kit that exports back to the same runtime.

**Try it.** With Docker (Linux containers; verified on Linux/amd64), build the image, download the package into a volume, and start the server:

```sh
git clone https://github.com/lutr0/openchoice.git
cd openchoice
docker build -t openchoice:cpu .
docker volume create openchoice-model
docker run --rm --mount type=volume,source=openchoice-model,target=/models openchoice:cpu download lutr0/OpenChoice-9B
docker run --rm --entrypoint python openchoice:cpu -c "import secrets; print('OPENCHOICE_API_KEY=' + secrets.token_hex(32))" > openchoice.env
docker run -d --name openchoice --env-file openchoice.env -p 127.0.0.1:8768:8768 --mount type=volume,source=openchoice-model,target=/models,readonly openchoice:cpu
docker logs -f openchoice
```

The container was verified on Linux/amd64; arm64 has only been tested under emulation. On Linux you can also skip Docker and use the native build described in the README.

Then send it a decision. We would like to hear where it fails.
